# 架构与设计取舍

## 数据流与线程边界

`Model.poll()` 每 0.5 秒调度一次读取。`reading` 防止同一 Model 并行提交多次读取；串行 `logQueue` 拥有 LogReader 的可变读取状态。后台生成 `Tracker.snapshot()`，主线程再替换可观察状态。`generation` 用于丢弃进入演示、恢复实时等操作之前提交的旧结果。

这比在视图里读文件多一个协调层，但避免磁盘读取和大量解析直接阻塞界面。当前快照会复制实体/事件容器；尚未做大规模性能分析，不声称恒定内存或固定端到端延迟。

## 日志生命周期

读取器选择最新会话，而不是简单选择“最后修改的 Power.log”：新客户端会话尚未产生 Power.log 时，回放旧对局会误导用户。

| 情况 | 行为 |
| --- | --- |
| 数据追加 | 从已保存的字节偏移继续读取 |
| 行未写完 | 保留尾部字节，下一批出现换行符后解析 |
| 文件变小 | 视为截断，重置偏移与对局状态 |
| 文件标识改变 | 视为替换，重置读取状态 |
| 新会话出现 | 跟随新会话，不退回旧对局 |
| 读取尚未追上文件 | 显示恢复进度状态 |

每批默认最多读 2 MiB，未完成行缓存超过 1 MiB 时丢弃。该保护限制异常行导致的缓存增长，也意味着超长有效行可能丢失；当前不支持把不完整日志恢复为完整事实。

## 实体状态与事件

`Tracker` 以实体 ID 为键维护卡牌 ID、控制者、区域与原始归属。GameState 与 PowerTaskList 可能输出同一事件，解析器在一次对局中选择单一日志流，避免重复计数。

出牌事件保留实体 ID 与事件发生时的卡牌身份。身份尚未揭示时，后续实体更新可以补齐；已知的历史出牌不会被之后的变形直接改写。生成牌不应被计为原始牌组已抽走的牌。这里维护的是日志支持的状态估算，不是完整的炉石规则引擎。

## 套牌匹配

`DeckLibrary.candidates` 用原始卡牌身份构造多重集合：不仅比较某张牌是否出现，还比较已观察副本数量是否超过保存构筑的数量。至少两张原始卡牌提供证据后才返回候选；原始牌库数量足够明确时还检查套牌张数。CORE、VAN、LEGACY 前缀做有限归一化。

- 唯一候选：显示自动匹配结果；后续证据仍可推翻它。
- 多个候选：清空完整构筑视图并继续等待，避免沿用错误的上一副。
- 无候选：显示日志已知卡牌，可由用户手动切换。

生成牌不参与匹配。此方法不能识别未保存的完整构筑，也不能从相同主牌推断不同备选牌；这些情况需要用户选择或新证据。

## 已知牌库顶

当前跟踪探底产生的关联实体，通过 CREATOR、LINKED_ENTITY、COPIED_FROM_ENTITY_ID 和 SHOW_ENTITY 关联候选及揭示。只有可关联的探底揭示才标记为已知牌库顶。普通 ZONE_POSITION 不代表可信的牌库顺序。

卡牌离开牌库、SHUFFLE_DECK 或 CREATE_GAME 会使标记失效。探底来源目前由中文卡牌效果文字识别，依赖本地中文数据；其他置顶机制与间接施放的复杂探底路径仍需更多日志验证。

## 本地存储

套牌使用 Codable JSON 和原子文件写入，先完成编码与写入，再更新导入后的内存状态。`deck.json` 自动迁移到 `decks.json`；同构筑去重，同名不同构筑保留版本。已有收藏文件无法解码时禁止覆盖，保留恢复机会。

文件体量和复杂度目前适合 JSON；尚无数据库、跨设备同步或多进程文件协调。随着收藏规模和查询需求增长，再决定是否引入数据库。

## 原生悬浮窗

AppKit `NSPanel` 负责浮动层级、跨空间显示、移动/缩放和点击穿透；SwiftUI 负责列表、预览和状态渲染。布局计算独立于窗口 API，可通过纯数值测试验证屏幕尺寸、负坐标和越界恢复。

点击穿透与卡牌交互互斥，因此设置中显式提供开关。自动化布局测试不等同于全屏、多个显示器及所有 macOS 版本的实机兼容性证明。

## 下一步拆分

当前 App.swift 同时承担界面、存储和收录协调；Decks.log 收录仍位于主线程的定期任务中。下一步计划抽离 DeckStore 与 CollectionReader，并给文件权限失败、坏文件和分段收藏日志补集成测试。为避免文档领先于实现，这些组件目前不列为已完成架构。
